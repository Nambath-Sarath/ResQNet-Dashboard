     1→     1→# ResQNet — Command Dashboard Web App Specification
     2→     2→
     3→     3→**Document type:** Product, UX, architecture, and implementation specification  
     4→     4→**Project:** ResQNet — Local-First Disaster Response and Resource Coordination Platform  
     5→     5→**Target host:** Raspberry Pi gateway/control center  
     6→     6→**Status:** Proposed design for implementation; not a claim that these features already exist  
     7→     7→
     8→     8→---
     9→     9→
    10→    10→## 1. Purpose
    11→    11→
    12→    12→The ResQNet Command Dashboard is the operator-facing web application used to monitor rescue nodes, review SOS reports, coordinate response work, inspect optional hardware modules, and manage local disaster-response information when internet access is unavailable.
    13→    13→
    14→    14→The dashboard is one client of the ResQNet backend. It is not the backend, database, or radio network itself.
    15→    15→
    16→    16→### 1.1 Core operating principle
    17→    17→
    18→    18→**Survivor Portal and Command Dashboard do not send data directly to each other.** Each client communicates with backend services. The backend validates requests, writes the authoritative records to the database, and distributes updates to authorized dashboard clients.
    19→    19→
    20→    20→- The **Survivor Portal** submits SOS reports, location information, messages, and resource requests.
    21→    21→- An **ESP32 node** provides nearby Wi-Fi access and forwards information over the configured node-to-gateway transport. If the gateway is unreachable, supported messages may be queued locally and forwarded later.
    22→    22→- The **Raspberry Pi** runs the API, database, event service, map service, and Command Dashboard hosting.
    23→    23→- The **Command Dashboard** retrieves records, shows live and last-known state, and sends operator actions back to the API.
    24→    24→
    25→    25→### 1.2 Goals
    26→    26→
    27→    27→1. Give operators one place to inspect the response situation and identify work requiring attention.
    28→    28→2. Receive and track SOS and other incident reports.
    29→    29→3. Register and monitor ESP32 nodes, their health, deployment locations, and capabilities.
    30→    30→4. Render node-specific module controls from validated capability reports instead of assuming all nodes have the same hardware.
    31→    31→5. Make stale data, disconnected nodes, and failed communication obvious.
    32→    32→6. Keep essential operations local and useful without internet access.
    33→    33→7. Maintain an auditable history of incident changes and sensitive operator actions.
    34→    34→8. Provide stable APIs so the Survivor Portal, nodes, and dashboard can evolve independently.
    35→    35→
    36→    36→### 1.3 Non-goals for the first release
    37→    37→
    38→    38→The first release should not claim to provide:
    39→    39→
    40→    40→- Guaranteed communication through rubble, water, or arbitrary distances.
    41→    41→- Precise survivor positioning based on the connected node's coverage area or Wi-Fi signal strength.
    42→    42→- General-purpose Wi-Fi repeating through a chain of single-radio ESP32 boards without a tested network design.
    43→    43→- Automatic identification of arbitrary hardware modules without an implemented discovery protocol.
    44→    44→- Fully autonomous rescue decisions or clinically reliable medical triage.
    45→    45→- Cloud dependence for core local operations.
    46→    46→- A production-grade, multi-region mission-control platform.
    47→    47→
    48→    48→These limitations should be reflected in the UI, documentation, and test plan.

    52→    52→## 2. Proposed technology stack
    53→    53→
    54→    54→Use a stack that is easy to develop, test, and run locally on a Raspberry Pi.
    55→    55→
    56→    56→| Layer | Proposed technology | Responsibility |
    57→    57→|---|---|---|
    58→    58→| Command Dashboard | React + TypeScript + Vite | Operator UI, navigation, client-side state, forms, filters |
    59→    59→| Styling | Tailwind CSS or CSS modules | Consistent responsive design and component styling |
    60→    60→| Routing | React Router | Page navigation and nested detail pages |
    61→    61→| Server-state cache | TanStack Query or a small typed API/state layer | Fetching, caching, retries, invalidation |
    62→    62→| Maps | Leaflet | Map interaction, markers, layers |
    63→    63→| Offline map data | Preloaded local tile package or another legally suitable offline map source | Maps without internet |
    64→    64→| API | Python + FastAPI | Authentication, validation, business rules, persistence, API and WebSocket events |
    65→    65→| Database | SQLite initially | Authoritative local records on the Pi |
    66→    66→| ORM/migrations | SQLAlchemy + Alembic, or equivalent migration tooling | Database access and schema evolution |
    67→    67→| Realtime updates | FastAPI WebSockets; REST fallback | New incidents, node health, messages, and status changes |
    68→    68→| Node firmware | ESP-IDF preferred; Arduino acceptable for a fast prototype | Node operation and hardware interfaces |
    69→    69→| Deployment | systemd services; reverse proxy only if needed | Reliable boot, restart, and local service management |
    70→    70→| Version control | Git | Code history, branches, reviews, releases |
    71→    71→
    72→    72→### 2.1 Frontend choice
    73→    73→
    74→    74→React is appropriate for the Pi-hosted dashboard because it contains several related, data-heavy pages, reusable tables and filters, live status indicators, maps, and dynamic module panels. Keep the ESP32 Survivor Portal much lighter; a small HTML/CSS/JavaScript page is generally a better fit for ESP32 memory and flash limits.
    75→    75→
    76→    76→### 2.2 Dependency policy
    77→    77→
    78→    78→Do not hard-code assumed “latest” library versions into this specification. At project setup, choose supported versions, pin dependencies in the lockfiles, record the Node/Python versions, and test the chosen set on the actual Pi. Avoid upgrading dependencies during an emergency deployment without regression testing.

   136→   136→## 3. System architecture
   137→   137→
   138→   138→### 3.1 High-level flow
   139→   139→
   140→   140→```text
   141→   141→                       LOCAL RESPONSE NETWORK
   142→   142→
   143→   143→ Survivor phone                                      Operator browser
   144→   144→      |                                                     |
   145→   145→      v                                                     v
   146→   146→ Survivor Portal                                     Command Dashboard
   147→   147→      |                                                     |
   148→   148→      | HTTP/API through a reachable local path             | REST + WebSocket
   149→   149→      v                                                     v
   150→   150→+----------------------+                       +--------------------------+
   151→   151→| ESP32 rescue node(s) | <--- node transport -->| Raspberry Pi gateway     |
   152→   152→| - local Wi-Fi access |                       | - FastAPI API            |
   153→   153→| - optional modules   |                       | - incident/business logic|
   154→   154→| - limited local queue|                       | - WebSocket event service|
   155→   155→+----------------------+                       | - SQLite database        |
   156→   156→                                               | - offline map assets     |
   157→   157→                                               | - built dashboard assets |
   158→   158→                                               +--------------------------+
   159→   159→```
   160→   160→
   161→   161→The diagram is conceptual. It does not define a working radio topology by itself. The node-to-Pi transport must be selected, implemented, and tested independently.
   162→   162→
   163→   163→### 3.2 The database is not connected directly to the web pages
   164→   164→
   165→   165→The recommended data flow is:
   166→   166→
   167→   167→1. A client sends a request to the API.
   168→   168→2. The API validates the identity, schema, and permissions.
   169→   169→3. The API applies business rules and stores the change in SQLite.
   170→   170→4. After the transaction succeeds, the API publishes an event to connected authorized dashboard clients.
   171→   171→5. The dashboard updates its view or refetches the authoritative record.
   172→   172→
   173→   173→Do not expose the SQLite file to browser JavaScript. Do not place database credentials in the frontend bundle.
   174→   174→
   175→   175→### 3.3 Where to host the dashboard
   176→   176→
   177→   177→Recommended initial deployment: build the React app into static assets and serve those assets from the Pi, using FastAPI static-file support or a small local web server/reverse proxy. Keep the API under a stable path such as `/api` and WebSockets under `/api/ws`. This makes the dashboard and API share the same origin and reduces CORS complexity.
   178→   178→
   179→   179→A separate web server is also acceptable, but its routing, origin, authentication, and offline behavior must be configured deliberately.
   180→   180→
   181→   181→### 3.4 Survivor Portal access is a separate networking problem
   182→   182→
   183→   183→Serving the Survivor Portal from an ESP32 does not automatically give it access to the Pi API. If the page and API are hosted at different addresses, browser origin rules, CORS, routing, and secure-context restrictions must be addressed and tested on actual Android and iOS devices.
   184→   184→
   185→   185→Browser geolocation generally requires a secure context. A plain HTTP page served by a local IP address may not be allowed to use the Geolocation API. Do not promise browser-based GPS sharing until the chosen portal delivery method has been tested. Possible alternatives involve a carefully configured HTTPS approach, a native app, or a different location-reporting workflow. Each has trade-offs, especially offline.
   186→   186→
   187→   187→### 3.5 Node-to-gateway transport must be explicit
   188→   188→
   189→   189→Choose and document one transport for the initial prototype:
   190→   190→
   191→   191→- **Wi-Fi/IP:** suitable when a node can join a local IP network and reach the Pi API.
   192→   192→- **ESP-NOW:** useful for compact vendor-specific peer messages, but it is not a standard IP bridge. A gateway service must translate messages into application records.
   193→   193→- **LoRa:** suitable for small, low-bandwidth payloads over a suitable radio link; not for normal web traffic, large images, or general IP bridging without extra infrastructure.
   194→   194→
   195→   195→Do not call an ESP32 chain a reliable internet mesh or Wi-Fi repeater unless that exact topology has been implemented and measured. Document range, obstacles, data rates, retry behavior, queue limits, and expected failure modes.

   199→   199→## 4. User roles and permissions
   200→   200→
   201→   201→Implement role-based authorization on the backend. Hiding a button in the frontend is not an authorization check.
   202→   202→
   203→   203→| Role | Typical permissions |
   204→   204→|---|---|
   205→   205→| Viewer | Read overview, maps, node state, and approved reports |
   206→   206→| Dispatcher | Review incidents, acknowledge, assign, update status, send approved messages |
   207→   207→| Field coordinator | Update assigned team/task status, submit field notes, view relevant resources |
   208→   208→| Node technician | Register nodes, inspect diagnostics, manage deployment references and modules |
   209→   209→| Administrator | Manage operators, configuration, backups, and all permitted operational functions |
   210→   210→
   211→   211→A small demonstration may begin with administrator and operator roles, but keep the permission checks centralized so the model can grow.
   212→   212→
   213→   213→### 4.1 Authentication requirements
   214→   214→
   215→   215→- Local authentication must work without an external identity provider.
   216→   216→- Store password hashes using a modern password-hashing library; never store plaintext passwords.
   217→   217→- Use secure session cookies or another carefully designed token strategy.
   218→   218→- Apply session expiration and logout.
   219→   219→- Protect state-changing requests against CSRF when cookie-based authentication is used.
   220→   220→- Rate-limit login attempts and externally reachable submission endpoints.
   221→   221→- Require stronger confirmation for destructive or high-impact actions.
   222→   222→- Record operator ID, time, action, and affected record in the audit log.
   223→   223→
   224→   224→### 4.2 Node identity is separate from operator identity
   225→   225→
   226→   226→A node should not authenticate merely by claiming a `node_id` in JSON. Provision a per-node secret, key, or another authenticated identity mechanism suitable for the chosen transport. Keep node credentials separate from operator sessions. If a radio transport cannot provide adequate security by itself, add message authentication, replay protection, and sequence/timestamp validation at the application layer.

   277→   277→## 6. Page-by-page functional specification
   278→   278→
   279→   279→## 6.1 Overview
   280→   280→
   281→   281→**Purpose:** Tell an operator what needs attention immediately.
   282→   282→
   283→   283→### Components
   284→   284→
   285→   285→1. **Network summary cards:** total nodes, online nodes, offline nodes, warning/fault nodes.
   286→   286→2. **Incident summary:** new SOS, unacknowledged SOS, incidents in progress, resolved incidents for a selected interval.
   287→   287→3. **Map preview:** recent reports and nodes, with a link to the full map.
   288→   288→4. **Priority queue:** incidents sorted by explicitly defined operational priority and age.
   289→   289→5. **Node health list:** last heartbeat, battery if available, last-known status, and warnings.
   290→   290→6. **Recent activity:** incident events, node connection events, module faults, and operator actions.
   291→   291→7. **Gateway health:** API/database status, storage capacity, last backup, and clock/synchronization health if available.
   292→   292→
   293→   293→### Behavior
   294→   294→
   295→   295→- Cards must be clickable where a useful filtered destination exists.
   296→   296→- Every live metric must expose its last-updated timestamp or have a clear page-level freshness state.
   297→   297→- If live data is not available, show “Last updated at …” and “Data may be stale”; never silently present old values as current.
   298→   298→- Avoid inventing an “AI recommendation” panel in the MVP. Add decision-support features only when their data, assumptions, and validation are defensible.
   299→   299→
   300→   300→## 6.2 Situation Map
   301→   301→
   302→   302→### Map layers
   303→   303→
   304→   304→- Node deployment references.
   305→   305→- Current node positions from a GPS module, where available.
   306→   306→- Survivor-provided locations.
   307→   307→- SOS/incidents.
   308→   308→- Shelters, supply points, and known safe locations.
   309→   309→- Optional manually marked hazards or operational zones.
   310→   310→
   311→   311→### Map behaviors
   312→   312→
   313→   313→- Marker clusters for crowded areas.
   314→   314→- Filters for time range, status, severity, node capability, and location source.
   315→   315→- Marker selection opens a details drawer with a link to the full record.
   316→   316→- Show a timestamp and accuracy/confidence where supplied.
   317→   317→- Distinguish locked deployment position, GPS position, manual position, and approximate node-associated search area.
   318→   318→- Do not infer a survivor's precise position from node range or signal strength.
   319→   319→- Show an explicit state when offline tiles are missing at the current zoom/area.
   320→   320→- Provide list/table alternatives for operators who cannot use the map or for locations that are not geocoded.
   321→   321→
   322→   322→### Offline map requirements
   323→   323→
   324→   324→- Do not depend on public online tile servers during an offline incident.
   325→   325→- Preload an appropriate map area and zoom levels, or use a licensed offline package.
   326→   326→- Check map data licensing and attribution requirements.
   327→   327→- Document storage required for each package and how to replace/update it.
   328→   328→- Cache assets deliberately; browser caching alone is not a complete offline map strategy.
   329→   329→
   330→   330→## 6.3 SOS and Incident Management
   331→   331→
   332→   332→### Incident fields
   333→   333→
   334→   334→- Unique incident ID.
   335→   335→- Incident/report category.
   336→   336→- Severity or priority and the rule used to set it.
   337→   337→- Status.
   338→   338→- Created, acknowledged, assigned, and resolved timestamps where applicable.
   339→   339→- Source type: survivor portal, operator, node, or import.
   340→   340→- Source node ID, if known.
   341→   341→- Reported coordinates, coordinate source, accuracy, and location timestamp.
   342→   342→- Text description and structured needs.
   343→   343→- Number of people affected, if reported.
   344→   344→- Assigned operator/team.
   345→   345→- Notes and attachments, if supported.
   346→   346→- Related/possible duplicate incident IDs.
   347→   347→
   348→   348→### Suggested statuses
   349→   349→
   350→   350→`NEW → ACKNOWLEDGED → ASSIGNED → IN_PROGRESS → RESOLVED`
   351→   351→
   352→   352→Optional terminal outcomes may include `CANCELLED` or `DUPLICATE`. Validate allowed transitions on the backend. Do not let a client set an arbitrary status string.
   353→   353→
   354→   354→### Incident UI
   355→   355→
   356→   356→- Filter by status, severity, category, team, time, and location.
   357→   357→- Sort by priority, then age; document the rule.
   358→   358→- Show unacknowledged incidents prominently without hiding older incidents.
   359→   359→- Provide an incident detail view with history and assignment.
   360→   360→- Require confirmation for resolve/cancel actions where appropriate.
   361→   361→- Record each transition in an append-only event/history table.
   362→   362→- Handle duplicate submissions with an idempotency key or stable client-generated submission ID where possible.
   363→   363→
   364→   364→### Critical delivery semantics
   365→   365→
   366→   366→A backend `201 Created` response means the Pi API committed the record, not that a field team has seen it. A node-side queue means “queued on node.” A destination acknowledgement is a separate state. The UI must not conflate these states.
   367→   367→
   368→   368→## 6.4 Survivor Registry
   369→   369→
   370→   370→- Temporary survivor ID.
   371→   371→- Reported name/contact only if voluntarily supplied and operationally needed.
   372→   372→- First seen/last contact times.
   373→   373→- Location with source, accuracy and timestamp.
   374→   374→- Reported needs and related incidents.
   375→   375→- Rescue/follow-up status.
   376→   376→- Related duplicate records and merge history.
   377→   377→
   378→   378→Use access controls and data minimization. A survivor report should not require a phone number or legal identity. Avoid showing sensitive contact data to roles that do not need it.
   379→   379→
   380→   380→## 6.5 Node Management
   381→   381→
   382→   382→### Node list columns
   383→   383→
   384→   384→- Node ID and optional operator-friendly name.
   385→   385→- Online/offline/stale/fault state.
   386→   386→- Last heartbeat.
   387→   387→- Battery or supply voltage, if reported.
   388→   388→- Current link metrics, if supported.
   389→   389→- Current reported module summary.
   390→   390→- Deployment location.
   391→   391→- Firmware and protocol version.
   392→   392→- Last known connected-client count, if supported.
   393→   393→
   394→   394→### Node details tabs
   395→   395→
   396→   396→1. **Overview:** identity, firmware, health, uptime, link state, heartbeat.
   397→   397→2. **Location:** locked deployment location, current GPS location (if present), accuracy, distance from reference and history.
   398→   398→3. **Modules:** discovered capabilities and per-module health.
   399→   399→4. **Events:** boot/reconnect, warnings, sensor faults, movement alerts.
   400→   400→5. **Configuration:** only supported, validated settings for the node.
   401→   401→
   402→   402→### Node lifecycle
   403→   403→
   404→   404→Suggested lifecycle: `REGISTERED → DEPLOYED → MAINTENANCE → RETIRED`. Online/offline state is a separate runtime state, not a replacement for lifecycle status.
   405→   405→
   406→   406→### Deployment reference coordinates
   407→   407→
   408→   408→Store deployment coordinates separately from live coordinates. Locking a reference location should store who set it and when. Updating it should require explicit permission and generate an audit event. A displacement alert must account for GPS accuracy, repeated readings, and a configurable threshold; a single noisy reading should not automatically establish that the node has moved.
   409→   409→
   410→   410→If no GPS module is present or no fresh fix is available, show the deployment reference and label current location as unavailable. Do not claim that the node has moved without evidence.
   411→   411→
   412→   412→## 6.6 Module Management and capability discovery
   413→   413→
   414→   414→The frontend should render only known, allowlisted module types and capabilities from a validated report.
   415→   415→
   416→   416→### Module states
   417→   417→
   418→   418→Use distinct states such as:
   419→   419→
   420→   420→- `PRESENT_ONLINE`
   421→   421→- `PRESENT_DEGRADED`
   422→   422→- `PRESENT_OFFLINE`
   423→   423→- `NOT_DETECTED`
   424→   424→- `UNKNOWN` (report absent, stale, invalid, or incompatible)
   425→   425→
   426→   426→Do not collapse “not detected” and “unknown.” A missing report is not proof that hardware is absent.
   427→   427→
   428→   428→### Example capability descriptor
   429→   429→
   430→   430→```json
   431→   431→{
   432→   432→  "protocol_version": "1.0",
   433→   433→  "node_id": "NODE-007",
   434→   434→  "firmware_version": "1.2.0",
   435→   435→  "hardware_revision": "A1",
   436→   436→  "reported_at": "2026-10-11T04:10:00Z",
   437→   437→  "modules": [
   438→   438→    {
   439→   439→      "module_id": "GPS-001",
   440→   440→      "type": "GPS",
   441→   441→      "status": "ONLINE",
   442→   442→      "capabilities": ["location", "speed", "utc_time"],
   443→   443→      "firmware_version": "1.0.2"
   444→   444→    },
   445→   445→    {
   446→   446→      "module_id": "CAM-001",
   447→   447→      "type": "CAMERA",
   448→   448→      "status": "ONLINE",
   449→   449→      "capabilities": ["photo_capture"],
   450→   450→      "firmware_version": "1.0.0"
   451→   451→    }
   452→   452→  ]
   453→   453→}
   454→   454→```
   455→   455→
   456→   456→This is an illustrative contract. Choose field names and allowed values once, put the schema under version control, and validate descriptors at the API boundary. The Pi should use the schema version and allowlisted registry to decide what to render.
   457→   457→
   458→   458→### Dynamic UI rules
   459→   459→
   460→   460→- GPS module with a valid fix: render coordinates, last-fix time, and quality fields the firmware actually reports.
   461→   461→- GPS module without a valid fix: render “GPS detected — no current fix,” not coordinates from an old reading without a stale label.
   462→   462→- Camera module: show camera controls only if the module supports the relevant operation and the operator has permission.
   463→   463→- IMU module: show only the movement/orientation measurements actually implemented in the firmware.
   464→   464→- No optional module: show core node health and deployment reference location.
   465→   465→- Unknown capability or incompatible protocol: show a safe diagnostic message; never execute arbitrary module-provided code.
   466→   466→
   467→   467→A physical expansion connector does not by itself create true plug-and-play discovery. Firmware, electrical interface, power limits, connector pinout, module IDs, and a discovery protocol must be designed and tested.
   468→   468→
   469→   469→## 6.7 Communications and Messages
   470→   470→
   471→   471→- Message ID, sender, recipient/group, type, creation time, body/payload reference, and delivery state.
   472→   472→- States should distinguish `CREATED`, `ACCEPTED_BY_GATEWAY`, `QUEUED_FOR_NODE`, `FORWARDED`, `ACKNOWLEDGED`, `FAILED`, and `EXPIRED` as applicable to the actual transport.
   473→   473→- Provide retries and expiry policy for supported messages.
   474→   474→- Limit payload size; route images through a deliberate attachment mechanism rather than blocking the emergency-message channel.
   475→   475→- Show failure reason and last attempt.
   476→   476→- Provide a clear indication when a broadcast was only accepted by the Pi, not acknowledged by receiving nodes.
   477→   477→
   478→   478→## 6.8 Resources and Shelters
   479→   479→
   480→   480→### Shelter fields
   481→   481→
   482→   482→- Shelter ID/name, coordinates, capacity, occupancy estimate, status, last updated time, and responsible operator/source.
   483→   483→
   484→   484→### Resource fields
   485→   485→
   486→   486→- Resource ID/type, unit, available quantity, reserved quantity if used, location, last updated time, and update source.
   487→   487→
   488→   488→### Actions
   489→   489→
   490→   490→- Create/update shelter and stock records.
   491→   491→- Record inbound requests.
   492→   492→- Assign and fulfill requests.
   493→   493→- Flag low stock by configurable thresholds.
   494→   494→- Audit manual adjustments.
   495→   495→
   496→   496→For the MVP, use explicit manual updates. Do not present estimated stock or occupancy as sensor-verified unless the relevant hardware has been implemented and validated.
   497→   497→
   498→   498→## 6.9 Reports and Audit
   499→   499→
   500→   500→Reports can include:
   501→   501→
   502→   502→- Incident totals by category, status, priority and time range.
   503→   503→- Acknowledgement/assignment/resolution durations.
   504→   504→- Node uptime and missed-heartbeat summaries.
   505→   505→- Battery and module fault history.
   506→   506→- Message forwarding and acknowledgement outcomes.
   507→   507→- Resource request/fulfilment totals.
   508→   508→- Operator audit trail.
   509→   509→
   510→   510→Allow CSV/JSON export for the first release. If a report contains personal or location data, require appropriate permissions and avoid exporting more detail than necessary. Clearly label data gaps caused by offline periods.
   511→   511→
   512→   512→## 6.10 System Settings
   513→   513→
   514→   514→- Operator management and role assignment.
   515→   515→- Node and capability protocol versions.
   516→   516→- Alert thresholds and heartbeat timeout.
   517→   517→- Gateway, database, and storage health.
   518→   518→- Backup and restore status.
   519→   519→- Offline map package inventory.
   520→   520→- Local time and UTC timestamp handling.
   521→   521→- Session policy and audit retention.
   522→   522→- Application build/version information.
   523→   523→
   524→   524→Configuration values should have safe bounds, validation, and audit entries. Do not expose arbitrary shell-command execution from the web UI.

   528→   528→## 7. Backend API contract
   529→   529→
   530→   530→All routes below are proposed. Implement and document request schemas, response schemas, permission rules, validation, pagination, and error codes before the frontend depends on them.
   531→   531→
   532→   532→### 7.1 Conventions
   533→   533→
   534→   534→- Prefix endpoints with `/api/v1` from the start to make future versioning explicit.
   535→   535→- Use JSON for ordinary API requests and responses.
   536→   536→- Use ISO 8601 timestamps in UTC, such as `2026-10-11T04:10:00Z`.
   537→   537→- Use stable string or UUID identifiers; do not depend on database row positions.
   538→   538→- Add pagination to list endpoints.
   539→   539→- Use query parameters for filtering and sorting.
   540→   540→- Return machine-readable error codes plus safe human-readable messages.
   541→   541→- Validate every input on the backend, even if the frontend validates it too.
   542→   542→- Use an idempotency key or client submission ID for retryable incident creation.
   543→   543→
   544→   544→### 7.2 Proposed endpoints
   545→   545→
   546→   546→| Method | Endpoint | Purpose / access |
   547→   547→|---|---|---|
   548→   548→| `POST` | `/api/v1/auth/login` | Authenticate local operator |
   549→   549→| `POST` | `/api/v1/auth/logout` | End session |
   550→   550→| `GET` | `/api/v1/auth/me` | Current user and permitted roles |
   551→   551→| `GET` | `/api/v1/overview` | Authorized overview metrics |
   552→   552→| `GET` | `/api/v1/health` | API health; minimize public diagnostic detail |
   553→   553→| `GET` | `/api/v1/nodes` | Filterable node inventory |
   554→   554→| `POST` | `/api/v1/nodes` | Register a node; technician/admin |
   555→   555→| `GET` | `/api/v1/nodes/{node_id}` | Node details |
   556→   556→| `PATCH` | `/api/v1/nodes/{node_id}` | Update allowed metadata/lifecycle fields |
   557→   557→| `POST` | `/api/v1/nodes/{node_id}/deployment` | Set or change deployment reference |
   558→   558→| `GET` | `/api/v1/nodes/{node_id}/events` | Node event history |
   559→   559→| `GET` | `/api/v1/nodes/{node_id}/capabilities` | Latest validated capability report |

   578→   578→
   579→   579→Avoid building all endpoints at once. Implement the routes required by the first end-to-end workflow, then expand.
   580→   580→
   581→   581→### 7.3 Example SOS request
   582→   582→
   583→   583→```json
   584→   584→{
   585→   585→  "client_submission_id": "phone-local-id-00042",
   586→   586→  "category": "RESCUE",
   587→   587→  "description": "Two people need assistance",
   588→   588→  "people_affected": 2,
   589→   589→  "location": {
   590→   590→    "latitude": 16.50,
   591→   591→    "longitude": 80.64,
   592→   592→    "source": "BROWSER_GNSS",
   593→   593→    "accuracy_m": 25,
   594→   594→    "captured_at": "2026-10-11T04:10:00Z"
   595→   595→  },
   596→   596→  "source_node_id": "NODE-007"
   597→   597→}
   598→   598→```
   599→   599→
   600→   600→Illustrative only. In production, coordinate fields must be range-checked, location source must use an allowlist, timestamps must be validated, and untrusted callers must not be allowed to impersonate a node merely by setting `source_node_id`. Do not treat example coordinates as real incident data.
   601→   601→
   602→   602→### 7.4 Example response
   603→   603→
   604→   604→```json
   605→   605→{
   606→   606→  "incident_id": "SOS-1042",
   607→   607→  "status": "NEW",
   608→   608→  "created_at": "2026-10-11T04:10:01Z",
   609→   609→  "accepted_by_gateway": true
   610→   610→}
   611→   611→```
   612→   612→
   613→   613→The API should acknowledge successful persistence only after the database transaction has succeeded. This response does not mean a team has received or acknowledged the incident.
   614→   614→
   615→   615→### 7.5 Error handling
   616→   616→
   617→   617→Use a consistent error envelope, for example:
   618→   618→
   619→   619→```json
   620→   620→{
   621→   621→  "error": {
   622→   622→    "code": "VALIDATION_ERROR",
   623→   623→    "message": "The submitted location is invalid.",
   624→   624→    "request_id": "req-example"
   625→   625→  }
   626→   626→}
   627→   627→```
   628→   628→
   629→   629→Expected cases include unauthenticated, forbidden, validation failure, not found, stale version/conflict, rate limit, duplicate submission, API unavailable, and storage failure. Do not reveal secrets or sensitive stack traces to the browser.

   633→   633→## 8. WebSocket event contract
   634→   634→
   635→   635→Use WebSockets to make the operator interface responsive, but do not make the WebSocket stream the only way data can be recovered.
   636→   636→
   637→   637→### 8.1 Envelope
   638→   638→
   639→   639→```json
   640→   640→{
   641→   641→  "event_id": "evt-1042",
   642→   642→  "event_type": "incident.created",
   643→   643→  "occurred_at": "2026-10-11T04:10:01Z",
   644→   644→  "schema_version": "1.0",
   645→   645→  "entity_id": "SOS-1042",
   646→   646→  "data": {
   647→   647→    "status": "NEW",
   648→   648→    "source_node_id": "NODE-007"
   649→   649→  }
   650→   650→}
   651→   651→```
   652→   652→
   653→   653→### 8.2 Event types to consider
   654→   654→
   655→   655→- `incident.created`
   656→   656→- `incident.updated`
   657→   657→- `incident.assigned`
   658→   658→- `node.status_changed`
   659→   659→- `node.heartbeat_received`
   660→   660→- `node.capabilities_updated`
   661→   661→- `node.displacement_warning`
   662→   662→- `module.status_changed`
   663→   663→- `message.delivery_updated`
   664→   664→- `resource.requested`
   665→   665→- `resource.updated`
   666→   666→- `system.health_changed`
   667→   667→
   668→   668→### 8.3 Reliability rules
   669→   669→
   670→   670→- Publish events after the corresponding database transaction succeeds.
   671→   671→- Include unique event IDs and timestamps.
   672→   672→- Reconnect with bounded exponential backoff and jitter.
   673→   673→- On reconnect, fetch changes since a known cursor or refetch the relevant list/detail. WebSocket delivery alone should not be assumed durable.
   674→   674→- Deduplicate repeated event IDs on the client.
   675→   675→- If events arrive out of order, use timestamps/version fields and refetch the authoritative record when needed.
   676→   676→- Limit WebSocket subscriptions by role and permitted data scope.
   677→   677→- Use REST polling as a fallback for critical views if WebSockets are unavailable.

   681→   681→## 9. Database design
   682→   682→
   683→   683→SQLite is a reasonable initial choice for a single Raspberry Pi prototype. Keep write transactions short and define backup and recovery procedures. SQLite is not a distributed shared database for every ESP32; the Pi hosts the authoritative database.
   684→   684→
   685→   685→### 9.1 Suggested tables
   686→   686→
   687→   687→| Table | Core fields (indicative) | Notes |
   688→   688→|---|---|---|
   689→   689→| `operators` | id, username, password_hash, role, active, created_at | Never store plaintext passwords |
   690→   690→| `nodes` | id, display_name, hardware_revision, firmware_version, protocol_version, lifecycle_state, deployment_lat, deployment_lon, deployment_locked_at, created_at | Locked reference location separate from live location |
   691→   691→| `node_heartbeats` | id, node_id, received_at, node_reported_at, battery, link_quality, uptime, health_state, connected_clients | Only fields the hardware actually reports |
   692→   692→| `node_locations` | id, node_id, latitude, longitude, accuracy_m, source, captured_at, received_at | Keep current/history separate from deployment reference |
   693→   693→| `capability_reports` | id, node_id, protocol_version, descriptor_json, valid, received_at, error_code | Preserve validated descriptor history as needed |
   694→   694→| `modules` | id, node_id, module_id, module_type, status, firmware_version, last_seen_at | Can be derived from latest report, but normalized records help history |
   695→   695→| `incidents` | id, client_submission_id, category, priority, status, description, people_affected, location fields, source, source_node_id, created_at, updated_at, assigned_to | Unique/idempotency constraint on stable client submission key where appropriate |
   696→   696→| `incident_events` | id, incident_id, event_type, old_value, new_value, actor_type, actor_id, created_at, note | Append-only incident history |
   697→   697→| `survivors` | id, temporary_reference, optional contact fields, first_seen_at, last_seen_at, status | Minimize personally identifying data |
   698→   698→| `messages` | id, source, destination, payload_reference, status, created_at, expires_at | Distinguish gateway acceptance from destination acknowledgement |
   699→   699→| `message_attempts` | id, message_id, attempted_at, outcome, error_code | Helps inspect intermittent links |
   700→   700→| `resources` | id, resource_type, unit, quantity, reserved_quantity, location, updated_at, updated_by | Use transactions to protect quantity updates |
   701→   701→| `shelters` | id, name, latitude, longitude, capacity, occupancy_estimate, status, updated_at | Clearly label estimates and source |
   702→   702→| `audit_logs` | id, actor_type, actor_id, action, entity_type, entity_id, timestamp, metadata | Restrict read access; avoid unnecessary sensitive payloads |
   703→   703→| `system_events` | id, event_type, severity, entity_type, entity_id, payload_json, occurred_at | General operational history |
   704→   704→
   705→   705→These are design-level fields, not a final migration. Normalize or combine tables based on implementation needs and query patterns. Add foreign keys, indexes, checks, and unique constraints deliberately.
   706→   706→
   707→   707→### 9.2 Database practices
   708→   708→
   709→   709→- Use migrations so the schema can evolve safely.
   710→   710→- Enable foreign-key enforcement.
   711→   711→- Use transactions for incident transitions, assignments, and resource quantity changes.
   712→   712→- Index common filter fields: status, created time, node ID, and incident priority where appropriate.
   713→   713→- Store UTC timestamps consistently; format them to local time in the UI.
   714→   714→- Define retention rules for location history, messages, attachments, and audit records.
   715→   715→- Back up to a separate storage location when possible, not only to the same SD card.
   716→   716→- Test restoring a backup; creating backups without testing restoration is insufficient.
   717→   717→- Avoid large binary image blobs in SQLite for the initial design; store files with controlled paths/metadata and reference them from the database if images are implemented.

   721→   721→## 10. Frontend behavior and state management
   722→   722→
   723→   723→### 10.1 State categories
   724→   724→
   725→   725→Keep different kinds of state separate:
   726→   726→
   727→   727→- **Server state:** nodes, incidents, survivors, resources, health data; fetched and invalidated through the API client.
   728→   728→- **Live event state:** connection status and event cursor; used to trigger updates/re-fetches.
   729→   729→- **UI state:** open modal, active tab, visible filters, table sorting.
   730→   730→- **Draft state:** unsaved form content; show when a draft has not been persisted.
   731→   731→- **Offline state:** last successful fetch time, stale flags, write capability, pending local client submissions where implemented.
   732→   732→
   733→   733→Do not treat data copied into React state as the source of truth. The backend remains authoritative.
   734→   734→
   735→   735→### 10.2 Shared reusable components
   736→   736→
   737→   737→Implement reusable components for:
   738→   738→
   739→   739→- `AppShell`, `Sidebar`, `TopBar`, `ConnectionBanner`
   740→   740→- `StatusBadge`, `SeverityLabel`, `FreshnessLabel`
   741→   741→- `DataTable`, `FilterBar`, `Pagination`
   742→   742→- `MapPanel`, `EntityDetailsDrawer`
   743→   743→- `AlertBanner`, `Toast`, `EmptyState`, `ErrorState`, `LoadingSkeleton`
   744→   744→- `ConfirmDialog`, `PermissionGate`
   745→   745→- `LocationField`, `TimestampDisplay`, `BatteryIndicator`
   746→   746→
   747→   747→These components should accept typed data and not contain unrelated API/database logic.
   748→   748→
   749→   749→### 10.3 Common page states
   750→   750→
   751→   751→Every data page should design for all of these states:
   752→   752→
   753→   753→1. Initial loading.
   754→   754→2. Successfully loaded with records.
   755→   755→3. Successfully loaded but empty.
   756→   756→4. Partial data with some unavailable fields.
   757→   757→5. Stale data due to lost connection.
   758→   758→6. API error with retry action.
   759→   759→7. Insufficient permissions.
   760→   760→8. Invalid or incompatible record.
   761→   761→
   762→   762→A blank table should not be the only response to every failure.
   763→   763→
   764→   764→### 10.4 Forms and destructive actions
   765→   765→
   766→   766→- Validate inputs for usability before submitting, then validate again on the API.
   767→   767→- Disable duplicate submissions while a request is pending.
   768→   768→- Preserve a user-entered draft after a transient error where safe.
   769→   769→- Show whether the backend accepted a write, not merely whether the button was clicked.
   770→   770→- Ask for confirmation before changing locked deployment coordinates, retiring a node, merging survivor records, or resolving/cancelling important incidents.
   771→   771→- Show the reason for a failure in language an operator can act on.

   775→   775→## 11. Offline and degraded-mode requirements
   776→   776→
   777→   777→Offline operation must have a precise meaning. The browser, Pi, and ESP32 nodes can lose connectivity independently.
   778→   778→
   779→   779→### 11.1 Dashboard-to-Pi outage
   780→   780→
   781→   781→- Show that the API is unreachable and mark displayed server data stale.
   782→   782→- Do not allow writes to appear successful while the API is unavailable.
   783→   783→- Reconnect automatically with backoff.
   784→   784→- Re-fetch authoritative records after reconnecting.
   785→   785→- Keep cached interface assets available if deliberately configured, but do not imply that cached records are current.
   786→   786→
   787→   787→### 11.2 Node-to-Pi outage
   788→   788→
   789→   789→- Nodes may queue a defined set of small messages locally.
   790→   790→- Each queued message needs an ID, creation time, retry/expiry rules, and an acknowledgement model.
   791→   791→- The node must have a documented storage limit and overflow policy.
   792→   792→- When the link returns, forward queued messages and handle duplicates idempotently.
   793→   793→- The dashboard should identify when a report was generated earlier but received later.
   794→   794→
   795→   795→ESP32 RAM/flash is limited. Do not assume every node can hold a full database, full offline map package, or unlimited images. Store only the small amount of data the chosen use case requires.
   796→   796→
   797→   797→### 11.3 Internet outage
   798→   798→
   799→   799→The core local dashboard and API should not depend on public internet services. Bundle frontend assets locally, use local DNS or a documented local address, preload required maps, and avoid CDN-hosted scripts/fonts needed for core operation.
   800→   800→
   801→   801→### 11.4 Clock problems
   802→   802→
   803→   803→Offline devices may have incorrect clocks. Keep both device-reported and gateway-received timestamps where useful. Display uncertainty if clock synchronization has not occurred; do not silently assume every device clock is accurate.

   807→   807→## 12. Location, movement, and data confidence
   808→   808→
   809→   809→Location is a safety-critical field and must not be displayed without context.
   810→   810→
   811→   811→Each location should ideally include:
   812→   812→
   813→   813→- Latitude and longitude.
   814→   814→- Source: browser GNSS, node GPS, manual entry, deployment reference, or approximate association.
   815→   815→- Capture timestamp and gateway receipt timestamp.
   816→   816→- Accuracy estimate, when available.
   817→   817→- Validity/fix state.
   818→   818→
   819→   819→Rules:
   820→   820→
   821→   821→1. Never call a deployment reference the current position unless the UI explicitly labels it as the reference position.
   822→   822→2. Never call a node's coordinates the survivor's exact coordinates.
   823→   823→3. A stale GPS reading must show its age.
   824→   824→4. A displacement alarm should incorporate reported GPS accuracy, multiple readings, and a threshold suitable for the hardware and environment.
   825→   825→5. An IMU may detect movement/tilt but does not provide absolute position on its own.
   826→   826→6. RSSI can be affected by walls, people, antenna orientation, interference, and multipath; do not present RSSI-based estimates as precise triangulation without experimental validation.
   827→   827→7. If no current position exists, preserve the SOS flow and clearly label location as unavailable or approximate.

   831→   831→## 13. Privacy and security requirements
   832→   832→
   833→   833→ResQNet may handle sensitive information about people in distress. Design privacy and security from the start, not as a final polish step.
   834→   834→
   835→   835→- Collect only fields needed for emergency response.
   836→   836→- Restrict survivor and precise-location views by role.
   837→   837→- Avoid putting sensitive data into ordinary application logs or error messages.
   838→   838→- Use authenticated sessions for operator pages and authorize all API actions server-side.
   839→   839→- Validate and limit every client/node payload size.
   840→   840→- Validate capability descriptors against a schema and an allowlist.
   841→   841→- Do not execute code, dynamic imports, or shell commands supplied by nodes.
   842→   842→- Authenticate node-to-gateway messages and consider replay protection.
   843→   843→- Use an expiry policy for queued messages that would become unsafe or irrelevant after a period.
   844→   844→- Audit sensitive reads/exports where operationally appropriate, plus all high-impact edits.
   845→   845→- Back up the database securely and control access to backup files.
   846→   846→- Keep dependency updates and firmware revisions traceable.
   847→   847→- Document how operators revoke a node credential if a device is lost or compromised.
   848→   848→
   849→   849→For a prototype, use synthetic test data until access controls, device authentication, backups, and data handling have been exercised.
   850→   850→

   852→   852→
   853→   853→## 14. Performance and reliability targets
   854→   854→
   855→   855→Set targets for the prototype and measure them on the actual hardware. The values below are suggested initial acceptance targets, not proven performance claims.
   856→   856→
   857→   857→- Dashboard initial load on the local network: target under 3 seconds on the test device/network.
   858→   858→- Routine API reads with modest local data: target under 500 ms at the 95th percentile on the Pi test setup.
   859→   859→- Once the API commits an SOS, the connected dashboard should ordinarily show it within 2 seconds under the tested LAN/WebSocket conditions.
   860→   860→- Reconnect without a full page reload after a short WebSocket interruption.
   861→   861→- Paginate large incident/event lists; do not load unbounded history by default.
   862→   862→- Never make a camera/image transfer block the primary SOS API path.
   863→   863→- Keep operational errors visible but do not flood the operator with duplicate alerts.
   864→   864→
   865→   865→Measurements must document Pi model, storage, network setup, number of simulated nodes, payload sizes, and test method. Revise targets if measurements show they are unrealistic.
   866→   866→

   869→   869→## 15. Accessibility and responsive design
   870→   870→
   871→   871→- Support keyboard navigation and visible focus states.
   872→   872→- Use text labels alongside colors and icons for statuses.
   873→   873→- Keep primary incident actions easy to find and large enough to operate under stress.
   874→   874→- Avoid color-only severity coding; use readable text such as “High” or “Unacknowledged.”
   875→   875→- Keep tables usable on laptop screens and provide a stacked/compact alternative on narrow displays.
   876→   876→- Provide clear confirmation for dangerous actions and an undo/correction path when practical.
   877→   877→- Use readable contrast, meaningful form labels, and appropriate ARIA labels where needed.
   878→   878→- Show timestamps in a consistent format and provide unambiguous date/time values in detail views.
   879→   879→- Avoid animation that distracts from incident priority; honor reduced-motion preferences.
   880→   880→
   881→   881→The dashboard is optimized for operators, but it may be opened on a tablet or phone during field work. The survivor portal is a separate, simpler user experience.

   885→   885→## 16. Testing strategy
   886→   886→
   887→   887→Testing must cover more than whether pages render.
   888→   888→
   889→   889→### 16.1 Frontend tests
   890→   890→
   891→   891→- Sidebar navigation and route protection.
   892→   892→- Empty, loading, error, stale, and partial-data states.
   893→   893→- Incident filters, sorting, pagination, and detail navigation.
   894→   894→- Role-based visibility for operator actions.
   895→   895→- Capability-driven module rendering from valid and invalid descriptors.
   896→   896→- WebSocket disconnect/reconnect and duplicate events.
   897→   897→- Form validation and duplicate-submit prevention.
   898→   898→
   899→   899→### 16.2 Backend tests
   900→   900→
   901→   901→- Authentication and role permissions.
   902→   902→- Schema validation for all request bodies.
   903→   903→- Incident lifecycle and valid/invalid status transitions.
   904→   904→- Database transaction rollback on failures.
   905→   905→- Idempotency for retried SOS submissions.
   906→   906→- Capability schema/version validation.
   907→   907→- Node identity and replay protection.
   908→   908→- Resource quantity consistency.
   909→   909→- Audit event creation for sensitive actions.
   910→   910→
   911→   911→### 16.3 Integration tests
   912→   912→
   913→   913→Test at minimum these flows:
   914→   914→
   915→   915→1. A simulated survivor submission reaches FastAPI and is persisted.
   916→   916→2. The dashboard sees the incident via WebSocket or its fallback and can acknowledge it.
   917→   917→3. The dashboard correctly handles an API restart.
   918→   918→4. A node reports a GPS-only descriptor and only GPS features appear.
   919→   919→5. A node reports GPS plus camera and both supported feature sets appear.
   920→   920→6. A node with no optional modules still displays its locked deployment reference.
   921→   921→7. An invalid or unsupported descriptor is rejected or safely marked incompatible.
   922→   922→8. A stale GPS value is displayed as stale, not current.
   923→   923→9. Node movement alerts require sufficient valid evidence and create an audit/event record.
   924→   924→10. A node loses its gateway link, queues a test message, reconnects, forwards it, and duplicate forwarding does not create duplicate incidents.
   925→   925→11. The Pi reboots and the database records persist.
   926→   926→12. A backup can be restored successfully.
   927→   927→
   928→   928→### 16.4 Field/network tests
   929→   929→
   930→   930→- Test the chosen radio topology in realistic distances and obstructions.
   931→   931→- Measure delivery latency, packet loss, retries, queue growth, and battery consumption.
   932→   932→- Test when some nodes are offline but others remain reachable.
   933→   933→- Test browser geolocation behavior on the actual Android/iOS device and portal origin.
   934→   934→- Test offline map coverage, tile storage, and UI behavior outside the downloaded area.
   935→   935→
   936→   936→Do not market the system as rescue-ready based only on UI or simulator tests. Real field deployment requires supervised hardware testing and an operational safety plan.

   941→   941→
   942→   942→The MVP is complete only when all relevant criteria below pass on the intended Raspberry Pi and node setup.
   943→   943→
   944→   944→### Dashboard foundation
   945→   945→- [ ] Operator can sign in locally and log out.
   946→   946→- [ ] Navigation works and unauthorized routes/actions are restricted by the backend.
   947→   947→- [ ] API/gateway state and data freshness are visible.
   948→   948→- [ ] Critical pages show loading, empty, failure and stale-data states.
   949→   949→
   950→   950→### Nodes and capabilities
   951→   951→- [ ] A node can be registered with a stable unique ID.
   952→   952→- [ ] Authenticated heartbeat reports update runtime state.
   953→   953→- [ ] The dashboard distinguishes online, stale, offline, and fault states.
   954→   954→- [ ] Deployment reference coordinates are stored separately from current location.
   955→   955→- [ ] The capability report is validated and versioned.
   956→   956→- [ ] GPS-only, GPS+camera, and no-optional-module cases are handled correctly.
   957→   957→- [ ] Unsupported or stale reports are shown as unknown/incompatible, not silently trusted.
   958→   958→
   959→   959→### Incidents
   960→   960→- [ ] A survivor-side test submission is saved in the Pi database when the configured network path is available.
   961→   961→- [ ] Retrying a request does not create duplicate incidents when the same submission ID is used.
   962→   962→- [ ] The dashboard receives or fetches the new incident.
   963→   963→- [ ] An authorized operator can acknowledge, assign, update, and resolve the incident.
   964→   964→- [ ] All important status changes are recorded in incident history and the audit trail.
   965→   965→- [ ] UI distinguishes local queueing, gateway acceptance, forwarding, and destination acknowledgement.
   966→   966→
   967→   967→### Offline/recovery
   968→   968→- [ ] Dashboard shows stale state when the API becomes unreachable.
   969→   969→- [ ] The client reconnects and refetches authoritative state after recovery.
   970→   970→- [ ] The node queue has a documented size limit, expiry policy, and duplicate-handling behavior.
   971→   971→- [ ] Essential frontend assets and configured map data work without public internet.
   972→   972→- [ ] Database backup and restoration are tested.
   973→   973→
   974→   974→### Security and privacy
   975→   975→- [ ] No browser client accesses SQLite directly.
   976→   976→- [ ] All state-changing API endpoints enforce authorization.
   977→   977→- [ ] Node identity is authenticated by the selected design.
   978→   978→- [ ] Logs do not unnecessarily expose sensitive survivor data.
   979→   979→- [ ] The operator can revoke compromised node credentials.

   983→   983→## 18. Recommended development order
   984→   984→
   985→   985→Build one functioning end-to-end slice before implementing every dashboard page.
   986→   986→

   988→   988→

   991→   991→3. Test browser geolocation on target phones and the chosen portal origin.
   992→   992→4. Define node identity and capability descriptor schemas.
   993→   993→5. Decide how local queued SOS reports are acknowledged and deduplicated.
   994→   994→

   996→   996→

   998→   998→
   999→   999→1. Set up the FastAPI app, SQLite database, migrations, and health endpoint.
  1000→  1000→2. Implement local operator login and authorization.
  1001→  1001→3. Add nodes and heartbeat records.
  1002→  1002→4. Add an incident-create endpoint with validation and idempotency.
  1003→  1003→5. Add basic audit records.
  1004→  1004→
  1005→  1005→### Phase 2 — Dashboard shell
  1006→  1006→
  1007→  1007→1. Create React + TypeScript + Vite app.
  1008→  1008→2. Build the responsive sidebar, top bar, connection banner, and routing.
  1009→  1009→3. Create a typed API client and common loading/error/empty components.
  1010→  1010→4. Build Overview, Node List, Node Details, and Incident Queue pages using real API responses.
  1011→  1011→
  1012→  1012→### Phase 3 — First end-to-end SOS flow
  1013→  1013→
  1014→  1014→1. Submit a test SOS through the Survivor Portal or a simple test client.
  1015→  1015→2. Persist the record on the Pi.
  1016→  1016→3. Publish a WebSocket event after successful persistence.
  1017→  1017→4. Display the incident in the dashboard.
  1018→  1018→5. Acknowledge and assign the incident from the dashboard.

  1022→  1022→
  1023→  1023→1. Implement descriptor schemas and validation.
  1024→  1024→2. Send reports from firmware or a simulator.

  1048→  1048→
  1049→  1049→Track these in the project README or an architecture decision log.
  1050→  1050→
  1051→  1051→| Decision | Why it matters | Required outcome |
  1052→  1052→|---|---|---|
  1053→  1053→| Node-to-Pi transport | Determines reach, throughput, payload size and gateway design | Chosen topology, protocol, retry strategy, and measured limits |
  1054→  1054→| Survivor Portal origin/hosting | Affects browser-to-API access and browser geolocation | Tested Android/iOS flow with documented limitations |
  1055→  1055→| Node authentication method | Prevents spoofed node reports | Provisioning, storage, rotation and revocation procedure |
  1056→  1056→| Capability protocol versioning | Allows firmware and dashboard to evolve safely | Versioned schema and compatibility policy |
  1057→  1057→| Offline message queue | Prevents loss/duplicates during intermittent links | Queue limits, expiry, acknowledgement and idempotency rules |
  1058→  1058→| GPS displacement rule | Prevents false movement alarms | Threshold, accuracy handling, confirmation readings, and alert cooldown |
  1059→  1059→| Offline map source/package | Determines coverage, storage, and licensing | Selected source, package process, attribution and update process |
  1060→  1060→| Data retention | Limits risk from sensitive survivor records | Retention periods, deletion/export permissions and backup policy |
  1061→  1061→| Backup target | Protects against SD card/Pi failure | Scheduled backup destination and tested restore procedure |
  1062→  1062→| Performance target | Gives a measurable acceptance standard | Test hardware, node count, workload, thresholds and results |

  1066→  1066→## 20. Practical first implementation checklist
  1067→  1067→
  1068→  1068→Use this checklist in the order shown. Avoid starting with animations, complex charts, or decorative dashboard cards before the data path works.
  1069→  1069→
  1070→  1070→- [ ] Create the repository and record the chosen hardware/network topology.
  1071→  1071→- [ ] Set up a repeatable development environment and dependency lockfiles.
  1072→  1072→- [ ] Create FastAPI `/api/v1/health` and SQLite migrations.
  1073→  1073→- [ ] Define typed API schemas and the node capability schema.
  1074→  1074→- [ ] Implement local login, roles, and audit events.
  1075→  1075→- [ ] Implement node registration and heartbeat updates.
  1076→  1076→- [ ] Implement incident creation, idempotency, state transitions, and history.
  1077→  1077→- [ ] Build the React app shell and API client.
  1078→  1078→- [ ] Build Node List, Node Details, and Incident Queue pages.
  1079→  1079→- [ ] Implement WebSocket updates and reconnect reconciliation.
  1080→  1080→- [ ] Connect a simulated node and a simulated survivor report before using real hardware.
  1081→  1081→- [ ] Connect one physical ESP32 using the selected transport.
  1082→  1082→- [ ] Test the portal on real phones, especially geolocation and local API access.
  1083→  1083→- [ ] Add offline map data and verify that no essential assets require public internet.
  1084→  1084→- [ ] Test outages, queue recovery, duplicate messages, backups, and permissions.
  1085→  1085→- [ ] Document exactly what has been tested and what remains unverified.
  1086→  1086→
  1087→  1087→## Final recommendation
  1088→  1088→
  1089→  1089→The first milestone should be deliberately small: **one authenticated operator, one registered ESP32 node, one working node-to-Pi path, one persisted SOS record, and one live dashboard update**. Once this works reliably under link loss and recovery, extend the same patterns to modules, mapping, messaging, resources, and reports.
  1090→  1090→
  1091→  1091→ResQNet should display only what its hardware and software can actually verify. Clear distinctions between current and stale data, approximate and precise location, queued and delivered messages, and absent and unknown capabilities are core functional requirements—not optional UI polish.
